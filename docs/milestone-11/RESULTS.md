## Existing persistence and recovery audit

Reviewed the existing Firebase architecture, Milestone 10 report, Milestone 4 private-beta/security findings, later Milestone 5 patched-runtime evidence and original preservation manifests before editing.

**Relational application records.** `app/db/session.py` already selects SQLAlchemy PostgreSQL with connection pre-ping and a bounded connection timeout; production refuses SQLite and PostgreSQL connection failure. Development deliberately permits PostgreSQL-to-SQLite fallback. Reused this boundary rather than adding a second repository layer. Existing ORM models and Alembic revisions 001–011 preserve owner, project, revision, authorization, audit and result relationships. JSON/spatial types, custom Stage 1 guards, constraints, defaults, sequences, timezone behavior and exact document hash serialization still need qualification on real PostgreSQL. Local SQLite is durable on its local filesystem but is not a Cloud Run persistence tier. No original schema or migration was executed.

**Historical databases and archives.** Existing retained archives/manifests cover multiple independent historical/test/evidence databases. They must not be combined automatically. Read-only comparisons reused those manifests in place; no original database was backed up, copied, restored or duplicated during this milestone.

**Files and evidence.** `app/services/storage.py` is the existing local/S3-compatible boundary. It is not a native Google Cloud Storage adapter. Some CAD and solver services also use direct paths independently of it. Saved revision/result source hashes and manifests exist, but filesystem writes and database result publication are not one distributed transaction. Existing S3 presigned URLs can last seven days; private Cloud Storage identity, generation preconditions, owner-checked retrieval, short-lived access and retention still need implementation/qualification. S3 compatibility does not prove GCS compatibility.

**Background jobs.** `app/services/jobs.py` uses Redis when available, with 24-hour status expiry, and otherwise an in-process dictionary. `app/workers/tasks.py` supplies Arq design-generation tasks. This is not yet a durable engineering queue/outbox. Memory fallback loses state on restart, Redis persistence/HA/expiry is unqualified, and queue retries/duplicate delivery are not an engineering authorization. Current engineering routes are synchronous, use process-local locks, commit authorization before solver execution, and persist artifacts/manifests/results in separate steps. A crash or database failure between those steps can leave uncertain execution. Their existing protection against retrying attempted proposals is preserved.

**Assistant.** `site_store.py` stores owner-scoped conversations, reservations and cumulative accounting in a separate SQLite ledger. `BEGIN IMMEDIATE` serializes reservation/settlement across connections sharing the same file. Expired RUNNING leases become INTERRUPTED while reservations remain charged conservatively; settlement is guarded against duplicate refunds. This provides useful single-host persistence. Separate SQLite files on separate Cloud Run instances would NOT share a global budget. Before multi-instance inference, move the whole reservation/check/settlement transaction to a qualified shared relational service, preserve cumulative historical reservations and block inference while that invariant is unproven. No new accounting store was introduced and paid inference remains disabled.

**Authentication.** M10's disabled Firebase verifier and separate audited identity-link metadata remain intact. The identity-link schema is not part of ordinary startup. Missing SDK, credentials, provisioning and live qualification still block Firebase sign-in. Linking by email, renumbering users or transferring projects is not permitted.

**Recovery.** Existing manifests and retained artifacts support integrity inspection, not a qualified offsite/point-in-time/cloud recovery service. RPO/RTO, encryption/key recovery, retention, backup scheduling, restore permissions, consistency across database/files/assistant ledger and real failover are unverified.

## Minimal delivered improvements

1. Existing local `save_file` now validates containment and publishes via a same-directory temporary file, flush, fsync and atomic replace. A failed flush/replace cannot expose partial new bytes or replace an existing final file with a partial write. Temporary publication files are removed on handled failures. This preserves successful local API behavior and stable keys. It is not a claim of full power-loss durability: directory fsync, disk guarantees, hard-kill orphan reconciliation and cross-store atomicity remain outside this bounded patch.
2. Production object storage now fails closed when configuration or initialization is unavailable, including cached failure. It never falls back to ephemeral local storage and never creates a bucket during production initialization. Local development retains its existing behavior. No cloud storage client was invoked during verification.
3. Added `app/services/recovery_policy.py`, a conservative decision-only boundary. It cannot dispatch, solve or grant execution. Completed duplicate delivery may return existing evidence only when authorization/source and complete hashes match. Uncertain attempts, partial manifests, stale sources, unavailable database/storage and failed/interrupted states require review or recovery. **Every decision has `may_execute=False`.** It is deliberately not wired into synchronous engineering routes or presented as an implemented queue.
4. Added reusable fail-closed browser routing in `frontend/e2e/support/isolated-routing.cjs` with focused regressions. The M11 harness uses it for both API and file assets, including legacy absolute GLB URLs. It refuses direct normal-API origins, original-project file prefixes, mutations, side-effect GETs and export-generation/download endpoints. The known read-only synthetic export-file listing remains permitted. Frontend resources/routes are allowlisted; unlisted paths fail instead of falling through to the original proxy.
5. The synthetic browser server rejects all non-read HTTP methods, skips startup initialization, clears provider credentials through the existing isolated configuration and marks responses with `X-Struvo-Test-Isolated: milestone-11`. The harness requires that marker and refuses redirects. The server source also asserts database/history/storage paths are within the retained synthetic root. Old historical harness files were not rewritten; they are evidence, not approved templates for new runs.

## Recovery contract for future workers

Use the existing current owner, exact saved revision, document/input/proposal/source hashes and explicit engineering authorization as the authority. A future durable job identity must bind these plus method/load-case and native solver version/artifact identity. Browser claims and queue delivery do not grant authority.

- **Before dispatch:** atomically record authorization-bound job identity and an outbox event in the relational transaction; unique constraints must prevent duplicate authorization consumption. No outbox schema was provisioned here.
- **On delivery:** claim the attempt transactionally with a fencing/lease identity; revalidate existing authorization/current source; return an already published exact result for duplicate completed delivery. Reject stale or foreign context.
- **After uncertain failure:** retain attempted state and all scratch/evidence; mark review required. Do not automatically rerun an engineering calculation, even if a queue retries or a lease expires.
- **Partial publication:** upload under immutable attempt/object identity with checksums and generation preconditions; publish the complete manifest only after every required object is verified. Database completion must reference exact object generations/hashes. Incomplete uploads remain quarantined and are not results. No automatic destructive cleanup is proposed.
- **Database outage:** do not publish success or acknowledge uncertain delivery as completed. Reconcile storage/attempt records after access returns; never infer that no database completion means no solver execution.
- **Storage outage:** do not expose completed results, switch silently to local storage or rerun. Retain existing evidence for manual reconciliation.
- **Restart/manual recovery:** inspect durable state, compare original authorization/source identities and manifests, then return existing evidence or require a new explicit proposal/authorization through the established workflow. A manual Retry is not permission to replay an uncertain solve.

Windows OpenSees is not assumed portable. Linux executable/container version, Tcl dependencies, resource bounds and all applicable independent numerical benchmarks must be qualified separately. Diagnostics may perform a version-only probe; no numerical solver test ran in M11.

## Candidate cloud compatibility and cost assessment

The previously selected architecture remains a candidate, not a deployment:

**Firebase App Hosting / Next.js.** Current Next 16.4.2 dynamic routes, Cesium workers/assets, streaming and same-origin API behavior need adapter/build qualification. Keep the frontend's local API proxy separate from future public metadata/domain. App Hosting requires Blaze billing; no billing was enabled. [Official framework support](https://firebase.google.com/docs/app-hosting/frameworks-tooling), [cost documentation](https://firebase.google.com/docs/app-hosting/costs).

**Firebase Authentication.** M10 identity verification and ownership mapping stay disabled. SDK installation, authorized project/provider/domain, credentials, session lifecycle and audited link provisioning require separate approval. No live sign-in is claimed.

**Cloud Run API/workers.** FastAPI can be a container candidate, but runtime filesystem data is not a durable cross-instance store. Existing loopback assumptions, process-local locks, background task lifetime and native Windows solver block direct deployment. Qualify request/job timeouts, worker concurrency/fencing, IAM and graceful termination. [Runtime contract](https://cloud.google.com/run/docs/container-contract).

**Cloud SQL PostgreSQL.** Existing SQLAlchemy/Alembic boundary is appropriate to investigate; use a synthetic database to validate all constraints, JSON/hash fidelity, sequence IDs, transaction isolation, pool limits, credentials and recovery before any original migration. No local PostgreSQL listener was reachable; no PostgreSQL restore/migration proof is claimed. [Cloud Run connection guidance](https://cloud.google.com/sql/docs/postgres/connect-run).

**Private Cloud Storage.** Native SDK is absent. Do not treat the existing S3 adapter as a verified GCS implementation. A separately approved adapter must preserve opaque keys plus exact generation/checksum identity, private access and application ownership gates. Generation preconditions protect against conflicting/repeated operations; they do not create a database/object transaction. [Official request preconditions](https://cloud.google.com/storage/docs/request-preconditions).

**Reviewed durable queue.** No queue was selected, provisioned or connected. Cloud Tasks is one candidate; duplicate execution is possible, so its delivery semantics cannot replace durable idempotency/fencing or authorization. Long native runs may require a controlled worker/job dispatch design rather than keeping an HTTP request open. [Cloud Tasks limitations](https://cloud.google.com/tasks/docs/common-pitfalls).

Cost blockers: App Hosting build/runtime/egress, Cloud Run worker CPU/memory/concurrency and uncertain retries, persistent Cloud SQL/storage/backups, private storage operations/versions/egress, queue operations, logs/monitoring, Firebase account verification requests, secrets and regional transfer. No fixed monthly estimate is asserted without region/workload/retention. Budget alerts are not assumed to be hard spending caps. Quotas, instance limits, parser/resource bounds and operational monitoring require separate review.
