The installed official Admin SDK can use `credentials.ApplicationDefault()` in that environment without a private key. This becomes acceptable only after the controlled-image, environment and identity checks below are implemented and approved. A generic ADC call on this Windows workstation remains forbidden. [Cloud Run service identity](https://docs.cloud.google.com/run/docs/securing/service-identity), [Admin SDK setup](https://firebase.google.com/docs/admin/setup).

Keep Cloud Run invocation IAM-restricted, with named test operators and no `allUsers` grant. A separately reviewed operator-controlled local proxy/test gateway can supply a Google invocation ID token in `X-Serverless-Authorization`, while forwarding the SDK-issued Firebase ID token unchanged in `Authorization`. These are two different trust boundaries; neither token replaces the other. No invocation token goes into browser storage. Exact proxy, origin, operator identity and ingress rules need approval and an offline review before browser acceptance. IAM-restricted invocation is not itself a private network. [Separate invocation header](https://docs.cloud.google.com/run/docs/authenticating/service-to-service).

## 2. Exact technical prerequisites

**Runtime Auth permission:** a reviewed project-scoped custom role containing `firebaseauth.users.get` for remote account/revocation checking. It is project-wide account-read authority, not an allowlist of test UIDs; dedicated-project isolation is mandatory. Do not grant runtime Owner, Editor, Authentication Admin, user mutation, email, key creation, signing or Token Creator permissions. Same-project attached identity needs no WIF provider, downloaded key or self-impersonation grant. [Auth permission mapping](https://docs.cloud.google.com/identity-platform/docs/access-control).

**Separate operators:** a deployer needs approved Cloud Run deployment authority, `iam.serviceAccounts.actAs` on this one runtime account, and image access; named invokers need `roles/run.invoker` on this service. A build/push principal may need repository-scoped Artifact Registry Writer; the Cloud Run service agent needs the documented image-pull permissions. Account/custom-role creation, IAM policy changes and API enabling are separate setup permissions and approvals, never runtime grants. Database, storage and secret-access permissions, if needed, must be independently scoped to the newly created resources. Do not grant broad roles to work around a failed qualification. [Deployment roles](https://docs.cloud.google.com/run/docs/deploying).

**Future managed-mode admission contract, not implemented here:**

1. Use a reviewed image digest and deployment manifest; omit `.env`, developer homes, Cloud SDK caches, service-account JSON keys, credential volumes and normal development data. Approve the runtime principal, service, revision, region and project number/ID together. Only trusted deployers may change this configuration.
2. Reject credential/source overrides before any ADC call: `GOOGLE_APPLICATION_CREDENTIALS`, Cloud SDK credential-directory overrides, emulator settings, metadata-host/IP/root overrides, unapproved proxies and conflicting Google project/quota settings. Before loading credentials, verify the managed metadata project and **actual default attached account email** against the approved project/principal using a bounded, fixed metadata destination, Google metadata headers, no redirects or ambient proxy. Do not treat `K_SERVICE`, an expected-email constructor argument, a credential object's initial `default` value or an application environment string as identity proof. This check relies on the trusted Cloud Run platform and reviewed deployment, not on cryptographic attestation supplied by an arbitrary local process.
4. Only then permit the official ADC path in the sealed managed image; accept the official metadata credential type only. No user/file credential or generic local fallback is allowed. Bind the Firebase app/cache to the exact project, credential mode and selected runtime identity. An unavailable or mismatched source fails startup/readiness before protected traffic. Later implementation must also prevent unreviewed metadata/proxy overrides during refresh.
5. Initialize the official Admin SDK with explicit `projectId=struvocivil-918c9`; retain `verify_id_token(..., check_revoked=True, clock_skew_seconds=0)` and existing issuer/audience/subject/lifetime and audited-link checks. Invalid/revoked/disabled tokens deny access; verification/network/configuration errors remain unavailable with no fallback. Account lookups add outbound latency, quota consumption and service dependence on every verification; do not cache a positive revocation result to bypass that policy.

No downloadable private key or homemade token verification is needed. These checks cannot protect against an authorized malicious deployer who can replace the image; restricting deployment/IAM is part of the trust boundary. Current Gate 2C code cannot be enabled for this architecture until a separately reviewed implementation satisfies this contract.
