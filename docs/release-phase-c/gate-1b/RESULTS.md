## Root-cause findings

1. **Gate1A initial root error was real:** dependencies linked outside the isolated root could not resolve `next/package.json`. Installed Next16.4.2 documentation confirms that resolution outside the project root needs a suitable root/additional-root boundary. Gate1A's additional-root experiment remained incomplete; that historical result is retained unchanged.
2. **Junctions were not the whole explanation:** Gate1B copied 64,116 installed dependency files (1,124,661,861 bytes), with no symlinks/junctions in the faithful frontend dependency copy. It used the byte-identical normal Next config, with no additional-root override. The first full build still stalled and was stopped at 180 seconds. After approximately 20 seconds, output stayed at 25 files/928,569 bytes, visible CPU time about 30 seconds and RSS about 1.39GB. This was a bounded compile-stage stall, not a successful build or indefinite wait.
3. **Core Node24/Turbopack works:** a minimal synthetic Next app without CSS built successfully. Adding the same PostCSS configuration reproduced a specific worker failure: `Node.js v22.18.0` and `Validation requires exact Node24.22.1`. Turbopack's CSS evaluation worker selected `node` from inherited PATH; explicitly invoking the main portable node.exe alone did not pin that worker. The guard rejected it before application/SDK loading. The probe has no Firebase/engineering imports. No mixed-runtime result is accepted as a PASS.
4. **Cold-output diagnostics mattered:** warm probe retries continued reporting the prior Node22 error after a process-local PATH prefix. Preserving that output and starting fresh exposed genuine Node24 workers plus the second issue below. This is evidence of stale generated/cache diagnostics in this test, not a general claim that every Turbopack cache is defective. Failed output was retained, not deleted.
5. **The validation network guard also blocked compiler IPC:** the generated PostCSS pool entry connects to an exact loopback port supplied on its command line. The old guard admitted only browser/API ports, so it rejected these compiler connections. The validation-only policy now admits 127.0.0.1 only when the entry is a generated isolated `pool_entry-*.js`, the requested port exactly matches its argument, and its parent PID matches the marked build process. It still denies external hosts, original website/API ports and unrelated files/processes. `ipc-policy-tests.json` has one allowed and 11 denied checks; no network is used by these policy tests. This is not a production authentication or API policy change.
6. **Full application passed with both corrections:** a PATH prefix only in the isolated subprocess environment and the narrowly owned IPC exception. All admitted Node runtime records are v24.22.1. No source/Next config change, Cesium-worker workaround, package substitution, Windows setting or system-wide PATH modification was needed. There is no demonstrated Node24/native-Turbopack, Cesium-static-asset or filesystem incompatibility in the tested configuration. The exact historical Gate1A stall is not retrospectively proven from its incomplete log alone; these causes were reproduced and resolved in Gate1B.

Diagnostic probes used one within-root dependency junction to the new physical tree and a narrow common-parent root; they are diagnostic controls, not the faithful full-app qualification. Their historical controller `physical_dependencies` field describes the backing dependency tree, not absence of that probe junction. The full app has no such link (`isolation.json`). The first controller attempt had a Windows backslash-quoting preload-path error, corrected to a forward-slash path before builds ran; a probe reporting step also initially expected a .ts config when the probe used .js. Neither is treated as an application failure. No guard/version check was weakened.

## Future transition proposal — not applied

A future approved launcher-only change can select the retained verified portable Node24.22.1 and its matching bundled npm, **prepend the portable runtime directory to PATH only within that launcher process**, and preflight both `process.execPath/version` and a spawned `node` worker. Use the installed Firebase engine floor >=24.12.0 while pinning the tested24.22.1. Current launchers' older minimum must be updated deliberately. Merely invoking the portable main node.exe leaves PATH-selected workers at risk.

Keep `npm run build`/standard Turbopack, existing ports/proxy/startup semantics, ownership and inference flags. Do not copy the validation guard, owned-IPC helper, fixture API port, probe root or `.next-beta` into the normal launcher. The IPC exception is needed by the restrictive test guard, not a new production service dependency. After an explicit launcher approval, verify the normal3001/8001 pipeline and normal-profile browser with isolated synthetic data before declaring the transition complete. Normal-runtime startup has **not** been switched or tested as if switched here.

Rollback remains immediate: use unchanged launchers/system Node22.18.0 and retained prior outputs; restore only an explicitly approved launcher change if one is later made. Do not downgrade Firebase or erase test/history data. Existing Node22 does not satisfy Firebase13.1's engine requirement; keep that integration disabled/unqualified until a deliberate transition and genuine authentication gates pass. `normal-node-unchanged.log` confirms v22.18.0 today.
