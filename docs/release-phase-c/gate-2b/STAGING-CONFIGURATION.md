## Project decision

Use exactly one dedicated non-production Firebase project and one reviewed web app. No candidate project ID or ownership evidence has been supplied, so **existing-project suitability is unknown**. An existing project is eligible only after its owner attests that it has no production users, customer data, shared applications, production IAM/credentials, production integrations or shared spending exposure; supplies reviewed provider/domain/IAM/billing configuration; and confirms authority to change it. A second app inside a production project is not sufficient isolation: apps share the project's authentication user database. [Project/user scope](https://docs.cloud.google.com/identity-platform/docs/concepts-manage-users).

If no candidate meets those requirements, a new dedicated project is required. Creation, adding Firebase to a Google Cloud project, web-app registration and any product upgrade remain separately gated. Do not discover projects using credentials or assume the existing website's branding implies a configured Firebase project. Record the approved project ID, project number and web-app ID in an operator-owned configuration record; no values are selected here.

An eligible candidate must also have no existing authentication subjects outside the newly approved synthetic manifest. Do not delete historical development/test accounts to make reuse qualify; choose a new project instead if that boundary cannot be met.

Distinguish the browser origin from SDK `authDomain`, which the current client restricts to the exact `<approved-project-id>.firebaseapp.com`. Firebase authorized domains are not a replacement for application CORS, TLS or server authorization; their configuration describes redirect domains, not a universal block on direct password API calls. [Config reference](https://docs.cloud.google.com/identity-platform/docs/reference/rest/v2/Config). Review any required Firebase-owned default action-handler domains; do not remove required entries blindly. Do not add wildcard, preview, production or unrelated test domains.

These are existing proxy controls, not changes to normal launchers. Approval must cover the isolated build output and configuration values before any real-service activation.

Local HTTP tests cannot qualify production HTTPS/HSTS, remote proxy trust or cloud infrastructure. Do not label the application production-ready or disable existing production guards to make localhost fit them. Before live testing, review a separate no-seed staging startup procedure that reuses existing routes/dependencies with newly provisioned data. Normal application development startup may seed data; the Gate 2A browser fixture server is also not a genuine staging launcher. If a full production-mode staging stack is chosen instead, its PostgreSQL/PostGIS, private storage, shared limiter and HTTPS prerequisites must actually pass.

## Proposed session policy

Retain Gate 2A `initializeAuth(...inMemoryPersistence)`: no Firebase refresh token is copied into the legacy localStorage token. A refresh/reload or closed tab loses browser sign-in; users must sign in again. Tabs hold independent sessions and may hold different users. Logout/account switching clears that tab's state; it does **not** promise immediate logout in another tab or server-wide revocation. The backend verifies each request and checks revoked/disabled accounts. A stolen ID token is not revoked by client-only logout. [Persistence](https://firebase.google.com/docs/auth/web/auth-state-persistence), [revocation](https://firebase.google.com/docs/auth/admin/manage-sessions).

F07 must test a separately signed-in second tab: it can remain authenticated after local logout in the first, but its next protected request must fail after approved server-side revocation. No persistence/cookie/BroadcastChannel redesign is authorized here. Production UX and security must explicitly accept this limitation or commission a separate design before activation.

In-memory persistence covers SDK authentication state, not all browser storage: existing view preferences/caches may use origin-shared localStorage. Cross-tab cache effects must be observed in F07 rather than inferred from token persistence. Memory-only tokens also remain exposed to malicious same-page JavaScript; this policy is not an XSS defense.
