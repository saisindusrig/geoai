# Gate 2B — IAM, credential custody and costs

**Proposed permissions, not granted roles.** An owner must approve named principals, exact resource scopes and time windows. Verify custom-role support and actual method permissions on the selected project; do not widen access automatically if a request fails.

## Separation of responsibilities

| Role | Narrow proposed capability | Exclusions / qualification |
| --- | --- | --- |
| Backend token verifier | Dedicated staging service account; custom-role candidate `firebaseauth.users.get` for revocation/disabled-account lookup | No create/update/delete/email/configuration/hash-export rights; no storage/DB admin or billing. This permission can expose other accounts in the same project, so dedicated-project isolation matters. |
| Authentication configuration operator | Human, time-limited `firebaseauth.configs.get` / `firebaseauth.configs.update`, plus required project inspection | Provider, domains, enumeration and signup restrictions only in the designated project. No routine user deletion, password-hash export, secret retrieval or billing changes. |
| Web-app registration operator | `firebase.clients.get`, `firebase.clients.list`, `firebase.projects.get`; `firebase.clients.create` only if separately approved | Review additional console-specific permissions individually. No unrelated app changes, project deletion or billing-plan update. |
| Synthetic-account lifecycle operator | `firebaseauth.users.get`, `firebaseauth.users.create`, `firebaseauth.users.update`; `firebaseauth.users.sendEmail` only for approved Admin email operations, `firebaseauth.users.delete` only for the separately approved disposable D case | Ordinary SDK reset requests are not secured by this IAM grant. IAM is not a per-test-UID allowlist: enforce a reviewed subject manifest and human checks; a project-wide grant can affect any project user. |
| Credential custodian | Deliver an already approved verifier credential; if a new service-account key is needed, separately approve `iam.serviceAccountKeys.create` on that single account | Never grant key creation to the web/backend runtime. Any later key disable/delete is a separate scoped rollback authorization. Keyless policy incompatibility means stop. |
| Internal link approver/provisioner | New staging internal admin plus narrowly reviewed database transaction rights for users/approval/link provisioning | Cloud IAM does not confer application admin status. Runtime cannot approve links, change roles or transfer owners. |
| Database/schema operator | Migration/DDL rights on the new staging database only | Runtime gets required application table/sequence rights, SELECT on links/users/approvals and permitted append-only audit operations; no DDL, role administration or historical DB grants. |
| Read-only evidence reviewer | Sanitized local acceptance evidence; narrowly scoped project metadata or cost view only if separately needed | No service-account keys, passwords, tokens, reset links, password-hash configuration or broad Owner/Editor/Authentication Admin access. |

Permission mapping derives from the [official Auth API access-control table](https://docs.cloud.google.com/identity-platform/docs/access-control) and [Firebase management permission reference](https://firebase.google.com/docs/projects/iam/permissions). `roles/firebaseauth.viewer` is a broader read-only fallback to review, not the proposed automatic runtime grant; it includes project/config inspection in addition to account reads. Broad Authentication Admin also includes sensitive capabilities the verifier does not need. [Role definitions](https://docs.cloud.google.com/iam/docs/roles-permissions/firebaseauth).

Do not grant service-agent roles to people or application principals. The current certificate-based verifier does not need custom-token minting, `signBlob`, Token Creator, cookie creation, password-hash retrieval, project creation or billing administration for ID-token verification. Console/project setup may require additional management capabilities; enumerate and separately approve these rather than assuming a runtime role covers setup.

## Current credential implementation constraint

`backend/app/core/firebase_auth.py:_sdk_verify` uses `credentials.Certificate(FIREBASE_AUTH_CREDENTIALS_FILE)` and checks that credential's project against configured identity. It does not implement ADC/Workload Identity Federation. Do not claim keyless operation or silently substitute a broader machine credential.

Prefer an already approved dedicated, short-lived staging key-delivery arrangement compatible with organizational policy. If policy disallows JSON private keys, this adapter cannot be activated as-is: obtain approval for a separately reviewed keyless change instead. Do not create a key to evade policy. [Key custody guidance](https://docs.cloud.google.com/iam/docs/best-practices-for-managing-service-account-keys).

A JSON private key is not intrinsically short-lived. An approved test end time must be paired with an enforceable expiry/revocation procedure; it is not evidence the key will expire automatically.

For an approved file-based test, a human custodian delivers it outside source, attachments, public assets, browser build paths, evidence directories and ordinary synced folders. Require reviewed encrypted local storage, restrictive OS ACLs and a distinct backend OS principal; frontend/build processes must not be able to read it. Running both under the same Windows identity does not create that isolation by itself. Privileged machine administrators remain a trusted, audited boundary.

Pass only the private file reference to the isolated backend. Frontend receives only reviewed public web configuration. Keep private values out of logs, CLI arguments, telemetry, HAR files, reports and screenshots. Use request counts/status codes and identity aliases as evidence; do not persist raw ID/refresh/OAuth tokens, reset action URLs or password bodies. A custodian validates official credential origin/project and approved token endpoint without revealing private contents. No credential file, environment entry, ACL or key was touched here.

Network approval must distinguish public documentation from actual use. Expected live families include SDK password/account calls to `identitytoolkit.googleapis.com`, token refresh to `securetoken.googleapis.com`, backend OAuth token exchange to `oauth2.googleapis.com`, Google's public signing-certificate endpoint under `www.googleapis.com`, and the exact approved auth action-handler domain. Inventory actual required endpoints before allowing traffic; do not permit all Google domains, proxies or arbitrary certificate endpoints. No such authentication calls were made in Gate 2B.

## Cost and availability approval

Default proposal: an eligible **unbilled Spark** candidate, no billing attachment, no plan upgrade and no paid add-on. The owner must verify its actual product/tier and that all mandatory controls are available. A reused billed project is not implicitly approved; a requirement for Identity Platform upgrade, paid anti-abuse controls or another service stops the plan pending a separate cost decision.

Base Firebase Authentication and Authentication with Identity Platform have different quotas/pricing. Published no-cost allowances do not prove this candidate is free or protected from quota exhaustion; [Firebase pricing](https://firebase.google.com/pricing) and [Identity Platform pricing](https://cloud.google.com/identity-platform/pricing) must be rechecked at execution. Phone/SMS, MFA SMS and federated-provider charges are outside the email/password proposal.

Password-reset delivery is a real service action, including possible mailbox-provider cost. Published reset-email quotas currently differ by plan (150/day Spark versus 10,000/day Blaze); they are not an application-specific abuse control or approved test volume. [Auth limits](https://firebase.google.com/docs/auth/limits). Approve recipient inboxes, action domain, message count and expiry/replay testing separately. No email is authorized or sent now.

The backend retains `check_revoked=True`, which adds an account-service round trip per verification; public certificate refresh and OAuth exchange also depend on availability. Do not disable revocation checks or accept cached positive identity as an outage workaround. Record real lookup failures/latency/quota behavior; no specific per-verification monetary price is assumed. [Revocation cost/availability](https://firebase.google.com/docs/auth/admin/manage-sessions).

PostgreSQL/Cloud SQL, private object storage, Secret Manager, Hosting/App Hosting, Functions, compute, load balancing, logging, outbound traffic and reCAPTCHA are separate products with separate prerequisites/costs. Installing `google-cloud-*` transitively with Admin SDK does not activate them or authorize their use. No cloud storage or SQL resource is needed merely to specify this auth plan; no cloud durability can be claimed from a local fixture.

Proposed operator/test-runner envelope for later approval: one project/web app; four synthetic Firebase accounts; at most 100 named SDK sign-in/refresh/account operations; 300 protected backend requests; six recovery messages; at most two initiated test operations/second; one expiry window of up to 75 minutes. Administrative changes and all actual wire requests must also be counted. SDK internal retries/certificate traffic may add requests: observe them and stop if the reviewed envelope cannot be maintained. These are test-runner limits, not hard service/billing caps, nor permission to provoke provider lockouts or exceed quotas.

Budget alerts are notifications, not evidence of enforced spending limits. Any separate spend-cap product must have its exact supported-service coverage, timing and failure semantics reviewed; none is assumed or configured. If a zero-new-charge envelope cannot be established, stop and seek an explicit amount, currency, product scope, operator and stop threshold. [Budget alert guidance](https://firebase.google.com/docs/projects/billing/budget-alerts). Paid Nebius inference and all numerical execution remain disabled regardless of Firebase approval.
