# Gate 2B — genuine F01–F07 plan

**All cases: NOT RUN.** This preserves the numbering and meanings in `docs/release-phase-b/STAGING-QUALIFICATION.md`. Gate 2A's 62 frontend / 62 backend tests are mocked or local evidence, not results for these cases. No live runner, user, key, inbox, database or service is configured by this document.

## Admission and evidence rules

Complete the independently scoped approvals in `APPROVAL-CHECKLIST.md` first. Record the designated owner/operator, project/web-app identity, permitted origins, exact subject registry, schema/fixture hashes, credential custody, request/mail envelope and rollback authority. No test may discover new accounts, expand privileges, enable billing or add products to solve a failure.

Use new subjects A/B (ordinary linked users), U (unlinked), D (disposable delete subject), and a separate new internal admin approver P0. Only controlled test inboxes are eligible. An unknown-address probe must also be in an owned test domain; never send to an uninvolved person's address.

Evidence per case: run ID, time/timezone, environment identity and SDK versions, subject alias, operation, expected/actual HTTP or sanitized SDK outcome, fixture identity/hash and relevant redacted audit correlation. Record PASS / FAIL / BLOCKED / INCONCLUSIVE individually. Never store passwords, credentials, raw bearer/refresh tokens, full HAR captures, reset links/codes or unredacted request bodies. Screenshots must omit secret fields and real mailbox contents. In-memory retained tokens are for the designated runner only.

Unexpected authorized access, registration, outbound product, billing requirement, original-data reference, download destination, solver/AI execution or identity-link write stops the run. Do not automatically retry mutations, raise quotas, relax gates or change expected outcomes to obtain a pass.

## F01 — genuine sign-in and verified identity

- **Operation/identities:** use the official browser SDK to sign in A and B. Submit actual SDK ID tokens to existing `/api/auth/me` and owned project reads. Exercise U, malformed/truncated and altered-signature tokens, a genuinely expired token, wrong expected configuration, and separately a valid token from another approved issuer if available. Test direct public signup denial before sharing any web configuration.
- **Expected:** exact linked internal A/B identities from the backend; no email/user-ID/role trust or ownership change. Invalid/expired tokens return 401; U returns 403; missing linking/configuration returns 503. No development header, legacy JWT, local password endpoint or demo route rescues Firebase mode. Direct end-user signup is rejected by the service, not merely by hidden UI or an unlinked-user 403.
- **Failure:** a wrong account resolves, any bad token grants access, an unknown identity is auto-created/merged, public signup succeeds, or a fallback is accepted. Distinguish wrong-project configuration failure from genuine wrong-issuer token rejection.
- **Additional approval:** G2B-01–G2B-06/G2B-08 below, including real sign-in/verification network traffic and named synthetic users. A genuinely signed wrong-project-token subcase needs a separately approved existing isolated helper issuer/new synthetic subject or another explicitly authorized source. No second project is created implicitly; without this, that subcase remains BLOCKED. Altering a token does not prove a signed wrong-project token was tested. Wait for real expiry in an approved timed window; do not change system time or forge expiry evidence.

## F02 — revocation, disable/delete and outages

- **Operation/identities:** retain A's pre-action ID token only in protected memory; allow distinct timestamp separation before operator revokes refresh tokens. Repeat on B with disable/re-enable. Deletion uses only D and only after a specific delete approval. Check old tokens on the same protected API/file/result/history gates. Exercise denied credential permissions, account-service timeout and unavailable certificate refresh through reviewed, isolated network controls.
- **Expected:** revoked/disabled tokens rejected (adapter 401), no fallback or old positive-verification cache; verification-service failure returns unavailable (503). Deleted subject must grant no access; the existing adapter does not explicitly classify every missing-user SDK error, so record the actual denied status rather than assuming 401. Fresh sign-in after permitted re-enable/recovery must not revive an inactive/unapproved internal link.
- **Failure:** any old token gets protected data, server skips revocation checks, an outage grants access, or unrelated accounts/credentials are affected. A 503 for a deleted user is not a successful sign-in; its UX/status policy still needs review.
- **Additional approval:** G2B-07 for exact UIDs and actions, credential/IAM scope and outbound lookups. Delete is independently opt-in and irreversible; re-creating an email is not restoring the old identity. Outage tests require scoped network-fault approval; do not edit machine-wide DNS, clock, firewall or real key contents. A warm certificate cache alone does not prove cold certificate-fetch failure behavior.

## F03 — logout

- **Operation/identities:** A signs in, opens project/history, starts delayed read/stream, then explicitly logs out. Attempt back navigation, pending completion and a no-token request; switch to B and inspect caches. Test a second independently authenticated tab.
- **Expected:** local ID/token state, account views, project/toast/view caches and pending requests are cleared/rejected; no A content appears in B's view. A new no-token API request returns 401. Original server-side records remain. The second tab may remain signed in under the proposed per-tab policy.
- **Failure:** previous-account content reappears, a stale 401 logs out B, a late sign-in resurrects A, legacy identity is used, or the UI claims global revocation from SDK logout alone. A retained pre-logout valid bearer may still work until expiry/server revocation: that is a documented limitation, not proof that local logout failed.
- **Additional approval:** G2B-06/G2B-08 live session scope. If global logout is required, G2B-07 must explicitly authorize revocation and its denial check; it is not part of ordinary local logout authority.

## F04 — password reset/change

- **Operation/identities:** after separate mail/recovery approval, enable only the isolated recovery UI flag and request reset for A plus an owned unknown-address probe. Use the reviewed official Firebase hosted action handler, recipient/domain binding, natural expiry, replay, wrong-recipient/wrong-project cases and old-token checks. Capture statuses/counts, not action URLs. Approve the action-handler host and inbox access before use.
- **Expected:** generic observable UI outcomes for known/unknown addresses, correct recipient/project/action scope, real expired/single-use action refusal and invalidated pre-change sessions at the backend. Observe actual provider abuse/quotas within the approved envelope. The frontend's generic success message is not proof an email was sent or a reset completed.
- **Failure:** enumeration through provider responses/timing, replay/expired reset acceptance, old sessions still authorized contrary to the chosen revocation policy, delivery outside the owned inboxes, or invented local recovery tokens. The SDK helper intentionally masks send errors; independent operator evidence must prove delivery and completed reset. If rate protection cannot be demonstrated within allowed traffic, mark INCONCLUSIVE; do not flood the service.
- **Additional approval:** G2B-07 mail recipients, maximum six messages, provider/action policy, password mutation and naturally timed expiry window. The app has no password-change form/action-code confirmation UI; use the official hosted reset path only if approved. Additional password-change tooling requires its own review. Provider reset-link lifetime must be recorded and observed, not assumed configurable or simulated with an emulator.

## F05 — recovery/account changes and link authority

- **Operation/identities:** review and approve a real reauthentication/recovery/account-change procedure for A before execution. Exercise changed email without relinking, old/new identity proof, link state revocation, mismatched audit metadata and internal approver-role revocation on new staging records.
- **Expected:** only the exact verified issuer/UID and approved internal association authorize access. No email-only merge, automatic ownership transfer, reused deleted UID, browser-supplied internal ID or self-approved admin link. Link/approver revocation denies access; new approval is an additional audited transaction, never an overwritten historical approval.
- **Failure:** recovery changes an owner or role without approval, stale links authorize, historical audit is edited, or manual console changes are presented as a completed application recovery flow.
- **Additional approval:** G2B-05/G2B-07 for exact internal/Firebase mutations and recovery identity policy. **Current blocker:** Gate 2A has a reset-request boundary, not a complete account-change/reauthentication/link-approval product workflow. F05 cannot be marked complete until that approved procedure/tooling exists and real evidence passes. Do not implement it in this approval phase.

## F06 — cross-user project/file/result/history isolation

- **Operation/identities:** A and B use newly created P_A/P_B, private files, synthetic saved-revision/result-identity records and separate history. Compare allowed own reads with denied other-owner requests; U, absent tokens, forged user/role/project fields and non-admin audit access must fail. Test protected downloads by reading fixture bytes in the runner, without triggering a browser file download.
- **Expected:** 401 when missing/invalid; 403 or intentionally non-disclosing 404 for another owner; no private content or metadata returned. Unknown/unlinked users are denied. Revision/source/hash/method/load-case binding is preserved; current/stale test records never imply real engineering verification. Original users/files/evidence/usage do not enter the environment.
- **Failure:** any cross-user read/mutation/download, stale-data substitution, role elevation, other-account history, unexpected original-data access, or write to an original ledger. Inspect newly isolated audit/accounting outcomes for expected test-only file events.
- **Additional approval:** G2B-05/G2B-08 for new fixture writes and limited safe metadata-mutation probes. Review handlers before execution. **Never probe solver/analysis/export/import execution routes expecting authorization to stop them:** an authorization defect could execute the prohibited workload. Restrict tests to existing reviewed read-only result/file/history gates and reversible synthetic metadata operations. This qualifies ownership, not numerical truth or cloud storage durability.

## F07 — browser session policy

- **Operation/identities:** A/B in independent tabs; reload/close/new-tab sign-in; SDK token refresh and naturally expired retained-token rejection; backend 401/403/503; account switching with delayed headers, bodies, aggregate project loads and assistant streams. Inspect only the new isolated browser profile for accidental persistence.
- **Expected:** in-memory per-tab behavior, reauthentication after reload, SDK token refresh without legacy storage, no cookie session or DEV fallback, no cross-tab identity/cache bleed. Ordinary logout affects its tab; approved server revocation is enforced on another tab's next protected request. Same-identity token refresh should not discard the editor draft. No token in query strings, localStorage, report or diagnostic output.
- **Failure:** durable Firebase refresh-token persistence, unintended shared account state, stale UI content, automatic request replay after rejection, invalid tokens accepted or provider outage treated as permission.
- **Additional approval:** G2B-06/G2B-08 session limitations and live timed window; G2B-07 only for global revocation. Local HTTP evidence does not qualify HTTPS/XSS defense in production. Any cookie/SSR/cross-tab global-logout redesign remains a separate approval and test scope.

## Rollback and stop procedure — proposed, not executed

1. Named operator stops the isolated staging ingress/frontend/API process trees or applies the previously approved private-network deny. Stop the runner and mail actions. Do not touch normal website/backend processes or shared projects. Confirm no protected staging requests can enter.
2. Keep `AUTH_REQUIRE_JWT=true`. Disable staging frontend/recovery flags and backend Firebase flag **while staging is offline**. The existing backend switches to legacy JWT mode when Firebase is disabled; therefore simply flipping that flag on a reachable staging service is not a safe rollback. Never enable DEV mock identity or start staging against the development database as a fallback.
3. After offline isolation, the credential custodian performs only explicitly pre-approved key disable/revocation or access removal for the exact test principal. The account operator performs only approved synthetic-subject revocation/disable actions. Stopping local processes does not revoke a stolen token/key or roll back cloud configuration.
4. Preserve test database, audit/link approvals, sanitized evidence and fixture manifests under the agreed private retention policy. Mark links inactive via a new approved audited transaction if required; retain historical approvals. Do not delete accounts, tables, project, files, logs or keys unless that exact action was separately authorized. No automatic restore/import or destructive cleanup.
5. Close the isolated browser profile; verify auth state and test ports are gone. Full reload also clears memory persistence, but other tabs and previously issued tokens still need the approved server-side revocation policy. Review any partial sends/resets/admin mutations; do not replay uncertain writes.
6. Re-enable only after the root cause, configuration diff, cost envelope, current credential custody and affected case reruns receive a new go decision. Retest freshness/ownership and compare original preservation manifests. No automatic restart, Firebase activation, cloud infrastructure continuation or public launch follows rollback.
